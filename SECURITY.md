# Security

## What this repository is

A demo invoicing app built to demonstrate how to embed an AI assistant safely. It holds no real
data: the ledger is generated by the seeder on first boot, and the three users are fixtures sharing
a published password. Nothing here is a service anyone depends on.

Some things that look like findings are deliberate, and are documented as such:

- **The default JWT signing key is in `docker-compose.yml`.** It exists so the demo runs before
  anyone has configured anything. Both the deploy compose file and `docs/deployment.md` require a
  real `JWT_SIGNING_KEY`.
- **The demo password is public.** It is printed on the login screen.
- **One seeded invoice carries a prompt injection in a line description.** That is a fixture. The
  injection eval cases read it back through `get_invoice`, and the frontend renders line text as
  text precisely so a mistake there would be visible.
- **The assistant calls the app's own API over HTTP.** That is [ADR 002](docs/adr/002-tools-via-http.md):
  it is what makes endpoint authorization apply to the assistant exactly as it applies to a browser.

## Reporting something

Open a [private security advisory](https://github.com/alexmartinezm/invoice-assistant/security/advisories/new).
Please do not open a public issue for anything you believe is exploitable.

Please report anything that breaks one of the invariants the repo is built to demonstrate. They are
listed in [AGENTS.md](AGENTS.md), and the reasoning is in
[`docs/adr/`](docs/adr/):

- a write reaching the database without a policy `allow` or a human approval recorded in
  `AuditEvent`;
- the assistant doing something the logged-in user could not do through the API themselves;
- a prompt that gets a tool call past `policies.json`, the per-turn limits, or the endpoint's own
  role and amount checks.

Please include a working example against a local `docker compose up` when possible. The eval cases in
`evals/cases/` show the expected format.
